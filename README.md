# Coding agent — все блоки до 10 баллов

Python 3.11+; единственная внешняя Python-зависимость — `certifi` для доверенных
HTTPS-сертификатов (проверка TLS остаётся включена). Для безопасного
исполнения Bash эта версия требует macOS с `/usr/bin/sandbox-exec`.
Другие ОС отклоняют Bash: небезопасного запасного режима нет.

## Установка после клонирования

Нужны Git и Python 3.11 или новее. Команда `python3` ниже должна запускать
именно эту версию Python. Полная демонстрация и системные проверки Bash
работают на macOS; поддержка других ОС для Bash пока не реализована.

```bash
git clone https://github.com/SmegCoder/hw_ai_agent.git
cd hw_ai_agent
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
```

В PyCharm откройте папку `hw_ai_agent` и выберите интерпретатор
`.venv/bin/python`. Если импорты `hw_ai_agent` подсвечиваются красным,
отметьте папку `src` через **Mark Directory as → Sources Root**.

## Справка в терминале

```bash
hw-ai-agent help                 # Краткая инструкция, команды и объяснение всех флагов
hw-ai-agent help tasks-demo      # Только аргументы выбранной команды
hw-ai-agent plan --help          # Та же подробная справка команды
```

Справка на русском доступна также через `hw-ai-agent --help` и запуск без аргументов.
Она не читает `.env`, не обращается к модели и не создаёт сессию. Например,
`--provider` предлагает три провайдера: `openrouter`, `openai` и `ollama`;
`--mode` объясняет подтверждения в Safe/Auto. Общий список флагов содержит
лимиты, планирование, задачи, журнал и восстановление; справка конкретной
команды показывает только поддерживаемые ею аргументы.

## Настройки в .env и команда set

Лимиты и параметры новых запусков можно хранить в `.env`. Для существующего
файла используйте `set`: он изменяет только указанные настройки, сохраняет
API-ключи и комментарии, записывает файл с правами `0600`. Если файла нет,
`set` создаёт его; ключи для платных провайдеров настраиваются отдельно.
Команда не вызывает модель и не проверяет подключение.

```bash
# Сохранить провайдера для будущих запусков:
hw-ai-agent set --provider ollama

# Сохранить модель именно этого провайдера:
hw-ai-agent set --provider ollama --model qwen3:4b-instruct

# Общие лимиты для всех новых запусков и демо:
hw-ai-agent set --max-rounds 30 --max-tokens 4096 \
  --max-tool-calls 128 --max-side-effects 32 --max-result-bytes 1000000

# Режим и дополнительные возможности:
hw-ai-agent set --mode safe --plan --tasks --journal
hw-ai-agent set --no-plan --no-tasks --no-journal

# Настройки отдельного профиля:
hw-ai-agent set --env-file .env.local --provider ollama --max-rounds 40
hw-ai-agent run --env-file .env.local --workspace ./my-project "Исправь ошибку"

# Только для одного запуска, без изменения .env:
hw-ai-agent run --workspace ./my-project --max-rounds 50 --max-tokens 8192 "Исправь ошибку"
```

Приоритет: **флаг запуска → переменная окружения → .env → встроенное значение**.
`set` записывает файл; уже экспортированная переменная окружения продолжает
иметь приоритет до её изменения или удаления. `--model` в `set` относится
к провайдеру из `--provider`, иначе к текущему провайдеру настроек.

| Переменная | Параметр |
| --- | --- |
| `AGENT_PROVIDER` | `--provider`: openrouter / openai / ollama |
| `<PROVIDER>_MODEL` | `--model`: OPENROUTER_MODEL / OPENAI_MODEL / OLLAMA_MODEL |
| `AGENT_MAX_ROUNDS` | `--max-rounds`: общий лимит запросов к модели, минимум 1 |
| `AGENT_MAX_TOKENS` | `--max-tokens`: выходные токены одного ответа, минимум 1 |
| `AGENT_MAX_TOOL_CALLS` | `--max-tool-calls`: вызовы инструментов, минимум 0 |
| `AGENT_MAX_SIDE_EFFECTS` | `--max-side-effects`: попытки записи/удаления/Bash, минимум 0 |
| `AGENT_MAX_RESULT_BYTES` | `--max-result-bytes`: байты результатов инструментов, минимум 0 |
| `AGENT_MODE` | `--mode`: safe / auto |
| `AGENT_APPROVALS` | `--approvals`: ask / deny |
| `AGENT_WORKSPACE` | `--workspace`: рабочая папка для run/plan |
| `AGENT_POLICY` | `--policy`: JSON-политика вне workspace; необязательна |
| `AGENT_STATE_DB` | `--state-db`: база сессий вне workspace |
| `AGENT_PLAN` | `--plan` / `--no-plan`: true / false |
| `AGENT_TASKS` | `--tasks` / `--no-tasks`: true / false |
| `AGENT_JOURNAL` | `--journal` / `--no-journal`: true / false |

`setup` добавляет общие значения по умолчанию, пример всех настроек находится
в `.env.example`. При отсутствии новых переменных прежние значения сохраняются:
обычные запуски — 12 запросов / 2048 токенов, workflow-demo и plan/rollback-demo —
20 / 2048, tasks-demo — 30 / 3072. Если соответствующая переменная задана,
она переопределяет эти значения во всех новых запусках.

Демо создают отдельные папки и не используют `AGENT_WORKSPACE`; явный
`--workspace` у демо должен указывать новую папку. Команда `plan` всегда
планирует, `tasks-demo` всегда использует задачи, `rollback-demo` всегда
включает журнал. `--offline`, паузы и намеренная авария задаются только
флагами конкретного запуска.

Начатая сессия сохраняет исходные модель, лимиты, режим, план и журнал:
`set` и изменение `.env` не меняют их при `resume`. `AGENT_STATE_DB` выбирает,
в какой базе искать сессию; если сменили путь, укажите прежний `--state-db`.
Справка: `hw-ai-agent help set`.

## Быстрый запуск с настоящим DeepSeek

После установки выполните из корня проекта в терминале с активированной `.venv`:

```bash
hw-ai-agent setup --provider openrouter
hw-ai-agent doctor --provider openrouter
hw-ai-agent demo --provider openrouter
```

Если `.env` уже настроен, пропустите `setup`: существующий файл не перезаписывается.
Чтобы использовать модель из `.env`, не передавайте `--model`.

Если `AGENT_MODE` не задан, используется `--mode safe`: запись файлов и Bash требуют
подтверждения каждого действия, даже если policy его разрешила.
Терминал покажет путь, diff и вопрос `[y/N]`: ответьте `y`, чтобы разрешить
только текущий вызов. Удаление тоже подтверждается каждый раз.
В `auto` запись и Bash выполняются сразу после проверок runtime и policy,
как указано в PDF. Каждое удаление подтверждается отдельно в обоих режимах.
Если для действия нужен ответ, но нет интерактивного stdin, запуск сохраняет
ожидающий вызов и останавливается с кодом 130; продолжите через `resume`
в терминале. Для узкого профиля демо:

```bash
hw-ai-agent demo --provider openrouter --mode auto --policy policies/demo.json
```

Этот профиль заранее разрешает только запись `order.py` и конкретную команду
тестов; остальные записи и команды запрещены. В Safe подтверждение требуется
даже при policy-`allow`. В Auto запись и Bash не требуют подтверждения;
`--approvals deny` не блокирует их, но отклоняет каждое удаление и другие
действия с обязательным подтверждением. Профиль демо запрещает удаление.

`setup` просит API-ключ через скрытый ввод и создаёт локальный `.env` с правами
`0600`. Ключ не нужно отправлять в чат. `.env` исключён из Git. Если файл уже
есть, setup откажется его перезаписывать: меняйте параметры через `set`
или редактируйте файл локально.
Переменные окружения имеют приоритет над `.env`.

`demo` **вызывает настоящую модель**. Для каждого запуска создаётся новая папка
`workspace/demo-<время>/`. Сначала программа убеждается, что исходные тесты
падают. Затем модель читает файлы, исправляет ошибку расчёта скидки и запускает
тесты через `Bash`. Программа отдельно повторяет проверку и сверяет SHA-256 теста.

Успех обозначается `DEMO PASS` и кодом завершения 0. Отчёт `demo-report.json`
содержит модель, вызовы инструментов, результаты до/после, diff и usage.
Утверждение модели «готово» само по себе не засчитывается. Для сдачи сохраните
отчёт своего успешного реального запуска.

Уже проведённая демонстрация DeepSeek завершилась успешно. Описание находится
в [результатах проверки](docs/DEMO_RESULTS.md), полный сохранённый отчёт —
в [docs/deepseek-demo-report.json](docs/deepseek-demo-report.json).
Эти два файла можно проверить после клонирования без API-ключа.

Без переопределений в `.env` или флагах ограничения обычного demo:
до 12 обращений, до 2048 выходных токенов на
обращение и до 120 000 символов истории. Автоматических повторов сетевых
запросов нет. Это ограничивает объём работы, но не является точным долларовым
лимитом; отдельный денежный лимит задайте в кабинете OpenRouter.

## OpenAI

Дополнительный ключ OpenAI не требуется для OpenRouter. При желании использовать
OpenAI напрямую добавьте `OPENAI_API_KEY` и `OPENAI_MODEL` в локальный `.env`:

```bash
hw-ai-agent demo --provider openai --model gpt-4.1-mini
```

Или сохраните отдельный файл конфигурации:

```bash
hw-ai-agent setup --provider openai --model gpt-4.1-mini --env-file .env.openai
hw-ai-agent demo --provider openai --env-file .env.openai
```

## Локальная Ollama

Установите Ollama из официального приложения или через Homebrew:

```bash
brew install ollama
ollama serve
```

Оставьте сервер запущенным; в другом терминале:

```bash
ollama pull qwen3:4b-instruct
hw-ai-agent doctor --provider ollama --model qwen3:4b-instruct
hw-ai-agent demo --provider ollama --model qwen3:4b-instruct --max-tokens 2048
```

Агент обращается к `http://127.0.0.1:11434/v1/chat/completions`. Платный ключ
в Ollama не передаётся. Instruct-модель загружается отдельно и занимает около
2,5 ГБ на диске. Её прежний успешный запуск контрольного демо сохранён
в `docs/session-ollama-demo-report.json`; он относится к предыдущей версии режимов.
Подключение само по себе не гарантирует результат: проверяйте `DEMO PASS`.

Ранее локальные прогоны с Thinking-вариантом `qwen3:4b` были медленными
и не подтвердили успешную демонстрацию. Наш клиент отправляет
`reasoning_effort=none`; результат зависит от конкретного установленного варианта.
В настройках по умолчанию и `.env.example` пока остаётся `qwen3:4b`, поэтому
для Instruct явно передавайте `--model qwen3:4b-instruct`, как в примере выше,
или задайте `OLLAMA_MODEL=qwen3:4b-instruct` в локальном `.env`.

`--max-tokens` ограничивает длину ответа, а не увеличивает контекст модели.
Увеличение до 20 000 может продлить генерацию. В исследованном локальном запуске
контекст составлял 4096 токенов; его размер настраивается отдельно в Ollama.
Сейчас `stream=false`, поэтому терминал показывает вызовы инструментов только
после получения полного ответа модели.

## Своя задача и workspace

```bash
hw-ai-agent run --workspace ./workspace "Прочитай файлы, исправь ошибку и запусти тесты"
```

В репозитории есть контрольный проект из PDF: `workspace/order.py` и
`workspace/test_order.py`. Для воспроизведения исходной ошибки запускайте `demo`: он создаёт отдельный
workspace с намеренно неправильной формулой.

Workspace — отдельная папка с файлами, над которыми работает модель.
По умолчанию используется `workspace/`, также поддерживается `AGENT_WORKSPACE`.
Папка должна существовать. Исходники агента лежат в `src/hw_ai_agent/`.

## Проверки

```bash
# Автономные проверки протокола, клиента, путей и управления процессами:
python -m unittest discover -s tests -v

# Обязательные проверки реальной системной защиты на Mac:
REQUIRE_SANDBOX_TESTS=1 python -m unittest discover -s tests -v
```

Без `REQUIRE_SANDBOX_TESTS=1` пропускаются 30 проверок реальной песочницы.
Это не эквивалент полной проверке перед сдачей.
Полный локальный прогон 13 октября 2026 года:
360 тестов прошли без ошибок и пропусков на Python 3.11.17 и 3.14.2, включая
22 проверки настроек в `tests/test_config_cli.py` и 15 регрессионных проверок
в `tests/test_runtime_regressions.py`.
В `.github/workflows/tests.yml` настроен запуск полного набора после push
или pull request на macOS и Python 3.11/3.13/3.14; это конфигурация CI,
а не свидетельство уже успешного запуска на GitHub.
Регрессионные тесты завершения Bash проверяют отказ `killpg` после выхода команды,
отказ для живого процесса и исчезнувшую группу процессов. Ошибка завершения
не скрывает успешный или обрезанный результат уже завершённой команды;
для живой команды отказ остановить группу возвращается как ошибка инструмента.

Ответы API в автономных тестах подставные; успешный платный или локальный запуск
подтверждается отдельно командой `demo`.

## Второй блок: policy и подтверждение действий

Требования сверены с приложенным «ДЗ_1_Coding_Agent.pdf». Реализованы
контроль разрешений `allow / ask / deny`, ограничения команд и директорий.
Описание проверок находится в [docs/POLICY_RESULTS.md](docs/POLICY_RESULTS.md).
Реальная демонстрация DeepSeek с узким профилем второго блока прошла успешно;
её [полный отчёт](docs/policy-deepseek-demo-report.json) содержит журнал решений policy.

Проверка без ключа и расходов на API:

```bash
hw-ai-agent policy-demo
```

Ожидаемый итог: `POLICY DEMO PASS`. Это детерминированная проверка runtime,
а не обращение к настоящей модели: подтверждения и отказы в ней подставные.

Правила проверяются в `ToolRuntime.execute()` до запуска каждого инструмента
модели. По умолчанию `list_files` и `read_file` разрешены. В `safe` каждый вызов
записи, Bash и удаления требует отдельного подтверждения.
В `auto` запись и Bash выполняются сразу после проверок, без первого
подтверждения. Каждое удаление подтверждается отдельно.
Явный `deny`, защита тестов и секретов, список команд и системная песочница
действуют в обоих режимах. Policy-`allow` не отменяет обязательные подтверждения
режима Safe и поштучные подтверждения удаления. Дополнительные ограничения
чтения policy также сохраняются.

Дочерние процессы `Bash` теперь работают без права записи файлов workspace:
даже импорт разрешённого `order.py` не может создать или изменить другой файл.
Записи выполняются только отдельным инструментом `write_file` после проверки
policy и нужного подтверждения. Это также запрещает файловые побочные эффекты
тестов, включая создание временных файлов. Шесть контрольных тестов демо
проверяют вычисления и работают в этом режиме.

Чтение открывает каждый каталог и файл через дескрипторы с `O_NOFOLLOW`.
Подмена файла или родительского каталога симлинком не перенаправляет чтение
вне workspace. Файлы с жёсткими ссылками отклоняются.

Ограничения чтения `read_file` также включаются в профиль системной песочницы.
Совпадения `deny` и `ask` закрывают соответствующие файлы для дочернего процесса;
подтверждение запуска команды не подтверждает чтение таких файлов. Для Bash
поддерживаются точные пути и шаблоны `*`/`?`; если ограничение чтения использует
неподдерживаемый шаблон с `[]`, запуск Bash отклоняется до создания процесса.

При совпадении нескольких правил приоритет: `deny` → `ask` → `allow`.
Если совпадений нет, применяется `defaults`; явное правило может разрешить
исключение из default-`deny`. Запреты runtime на тесты, секреты, выход из
workspace и запрещённые команды нельзя отменить правилом `allow`.

Загруженный через `--policy` файл является полной конфигурацией: пропущенное
разрешение инструмента означает `deny`, а отсутствие `directories.allow` не
разрешает ни одной директории. Встроенный профиль без `--policy` и программный
`Policy.from_dict()` сохраняют свои исходные значения по умолчанию. Для строгого
программного разбора используйте `Policy.from_dict(data, fail_closed=True)`.
После подтверждения действия runtime повторно проверяет актуальную policy,
путь и идентичность рабочей директории Bash; изменение цели отменяет вызов.

Готовые JSON-профили:

| Профиль | Поведение |
|---|---|
| [policies/readonly.json](policies/readonly.json) | Только файловое чтение; запись и команды модели запрещены |
| [policies/review.json](policies/review.json) | Файловые изменения и ограниченный набор команд; подтверждения по режиму; `private` запрещён |
| [policies/demo.json](policies/demo.json) | Запись только `order.py` и запуск только `python -m unittest discover -v` |

Пример чтения проекта:

```bash
hw-ai-agent run --workspace ./workspace --policy policies/readonly.json "Опиши файлы проекта"
```

Пример работы с подтверждениями:

```bash
hw-ai-agent run --workspace ./workspace --policy policies/review.json "Проверь код и предложи исправление"
```

Файл политики должен лежать вне выбранного workspace. Он загружается до работы
агента; значения действий и поля JSON проверяются, ошибочная конфигурация
прерывает запуск. Имена инструментов: `list_files`, `read_file`, `write_file`, `delete_file`,
`Bash`. Поле `directories.allow` перечисляет разрешённые директории и их потомков,
`directories.deny` — запрещённые; запрет имеет приоритет. Пути относительные,
внутри workspace, без `..`, шаблонов и симлинков в настройке. В примерах
разрешён workspace (`.`), запрещён `private`. Не перечисленные в `allow`
директории отклоняются; правила действуют для файлов, списка и Bash, включая
чтение внутри дочернего процесса. `policies/demo.json` разрешает одну команду
тестов и явно запрещает `sleep 0`; остальные команды отклоняются default-`deny`.
`Bash(command, cwd)` принимает относительную рабочую директорию; по умолчанию `.`.

У `unittest` проверяются также пути внутри `-s`, `-t`, `--start-directory` и
`--top-level-directory`, включая формы `-sdir` и `--start-directory=dir`,
и директории из имён модулей вроде `package.test_order`. Разрешены обычные
флаги `-v/-q/-f/-c/-b`, их полные длинные формы, `--locals`, справка, а также
шаблоны `-p/--pattern` и `-k`. Неизвестные и сокращённые длинные параметры
отклоняются до запуска процесса. Шаблоны передаются как данные, без раскрытия Bash.
Команда запускается через Bash после разбора, результат содержит `stdout`,
`stderr` и `exit_code`. Ограничение вывода общее для двух потоков.

Поле `path` сопоставляется с разрешённым каноническим путём относительно
workspace, поле `command` — с полной командой после разбора аргументов.
Шаблоны используют `fnmatch`; `*` может включать вложенные части пути.

В `safe` разрешения всегда разовые, включая продолжение через `resume`.
В `auto` разрешения на сессию не нужны: запись и Bash выполняются сразу
после проверок и при новом запуске, и после `resume`. Удаление требует нового
подтверждения при каждом вызове; старые разрешения на сессию не используются.
Для запроса записи в Safe показываются diff (до 4000 символов) и SHA-256.
Удаление доступно только для обычных файлов: тесты, секреты, каталоги, симлинки
и файлы с жёсткими ссылками защищены. Файл перемещается в закрытую папку
`.agent/trash/RECOVERY_ID/file` вне workspace; `info.json` хранит исходное размещение.
Восстановление возможно копированием сохранённого файла в прежнее место;
автоматического отката нет. Между разными файловыми системами перенос отклоняется.
Отказ или ошибка обработчика подтверждения блокирует
действие и возвращается модели как `APPROVAL_REQUIRED`; явный запрет —
как `POLICY_DENIED`. Решения печатаются в терминал и сохраняются в
`policy_events` отчёта демонстрации без содержимого файлов.

Подтверждение записи связано с канонической целью и состоянием файла.
После подтверждения повторно проверяются путь, файл и родительские каталоги.
Смена симлинка, замена файла или ручная правка во время ожидания возвращают
`TARGET_CHANGED`; требуется новый запрос с новым просмотром изменений.
Файл открывается через проверенные дескрипторы каталогов без следования
симлинкам, а изменение начинается только после проверки открытого файла.

Регрессионные проверки в `tests/test_policy_security.py` воспроизвели оба
обхода на старом коде и проходят на исправленной версии. В них также есть
исходная демонстрация с подставной моделью и настоящими инструментами.

Подготовка демо и независимая проверка тестов выполняются доверенным кодом
приложения. Политика управляет запросами модели через `execute()`; прямые
методы runtime предназначены для этого доверенного кода.

## Третий блок: сохранение и восстановление сессии

Команды `run` и `demo` автоматически сохраняют задачу, историю, вызовы
инструментов, результаты и события в `.agent/sessions.sqlite3`. ID сессии
печатается в начале. База находится вне workspace, исключена из Git и создаётся
с правами `0600`; новый каталог `.agent` имеет права `0700`.
API-ключ из настроек не сохраняется. База не зашифрована и содержит рабочую историю.

Проверка без API-ключа:

```bash
hw-ai-agent session-demo
```

Ожидаемый итог — `SESSION DEMO PASS`. Подставная модель и настоящие инструменты
показывают остановку после сохранённой записи, открытие новой базы и выполнение
оставшихся тестов без повторной записи.

Демонстрация на настоящей локальной модели:

```bash
hw-ai-agent demo --provider ollama --model qwen3:4b-instruct --policy policies/demo.json --stop-after-tools 1
hw-ai-agent sessions
hw-ai-agent session SESSION_ID
hw-ai-agent resume SESSION_ID
```

Замените `SESSION_ID` на напечатанный ID. Первая команда намеренно завершается
кодом 130 после первого сохранённого результата. Флаг остановки не наследуется
при `resume`. Можно также использовать `Ctrl+C`. Новый `demo` создаёт новую задачу;
для продолжения старой нужен `resume`.
Остановка и продолжение с настоящей `qwen3:4b-instruct` проверены:
получен `DEMO PASS`. [Сохранённый отчёт](docs/session-ollama-demo-report.json)
содержит события до и после остановки в одной сессии.

В сохраняемых `demo-report.json` персональные пути очищаются автоматически:
workspace обозначается как `workspace/demo`, домашний каталог — `<home>`.
Очистка применяется и к вложенным событиям, ошибкам и выводу тестов.
Она не удаляет секреты из произвольного текста — просмотрите отчёт перед публикацией.
Локальный журнал `.agent` сохраняет настоящие пути для восстановления сессий;
его нельзя публиковать.

`--state-db` задаёт свой путь базы; передавайте его и командам просмотра,
продолжения и разрешения неопределённых вызовов. База должна быть вне workspace.
Пользовательский путь размещайте вне Git или отдельно исключайте из `.gitignore`.
При продолжении сверяются workspace, policy, модель, адрес сервера и лимиты.
Счётчик обращений не сбрасывается; режим сохраняется. В `auto` запись и Bash
сразу проходят проверки и исполняются; в `safe` каждый следующий изменяющий
вызов и Bash подтверждаются заново. Удаление подтверждается поштучно.

Завершённые вызовы пропускаются. Любой инструмент, начатый до сбоя и не имеющий
сохранённого результата, становится `uncertain`: автоматическое продолжение
блокируется до решения оператора, даже для чтения и в режиме `auto`.
Вызов, ещё не начатый (`pending`), и вызов в ожидании ответа (`awaiting_approval`)
не являются неопределёнными. Ожидание подтверждения сохраняется до вопроса:
если закрыть терминал или нажать Ctrl+C в этот момент, `resume` повторит вопрос.
Ответ `n` возвращает модели ошибку инструмента и сохраняется в журнале.
`retry` фиксирует новую попытку того же вызова. Повтор завершённого
`tool_call_id` возвращает сохранённый результат без нового действия; смена
имени или аргументов этого ID вызывает ошибку протокола.

```bash
hw-ai-agent session SESSION_ID
hw-ai-agent resolve SESSION_ID --call 1:0 --resolution applied
hw-ai-agent resume SESSION_ID
```

`1:0` — пример; берите ключ из `unfinished_calls`. `applied` принимается только
при совпадении текущих байтов файла с запрошенной записью. `retry` явно разрешает
повтор с новой проверкой policy и требований выбранного режима.
`skip` сообщает модели об отказе от повтора и не откатывает возможные изменения.
`abort` завершает сессию с ошибкой (`aborted`), возвращает код 1 и запрещает `resume`.
Текущие инструменты читают данные, полностью заменяют файл заданным содержимым
либо перемещают файл в восстановимое хранилище (повтор отсутствующего — без эффекта);
повтор неизвестного инструмента без поддержанного контракта запрещён.

## Многофайловое демо с настоящей моделью

Запускайте из корня проекта с активированной `.venv`. По умолчанию демо вызывает
настоящую модель и создаёт восемь файлов: рабочие модули, тесты и неиспользуемые
модули. Промпт просит исправить и оптимизировать код, сообщает о доступных
инструментах, но не указывает кандидатов на удаление.

```bash
hw-ai-agent workflow-demo --provider openrouter --mode safe
hw-ai-agent workflow-demo --provider openrouter --mode auto
```

Модель OpenRouter берётся из `.env`; запуск платный. В `safe` подтверждайте
каждую запись, Bash и удаление. В `auto` подтверждайте только каждое удаление;
запись и Bash выполняются сразу после проверок. Отказ не выполняет действие.
`--approvals deny` отклоняет все новые запросы подтверждения. Для локальной модели:

```bash
hw-ai-agent workflow-demo --provider ollama --model qwen3:4b-instruct --mode auto
```

`workflow-report.json` отдельно показывает функциональную корректность и
оптимизацию. Для полного `WORKFLOW DEMO PASS` должны пройти четыре теста без
изменения контрольного файла и исчезнуть минимум два из трёх неиспользуемых
модулей. Имена и критерий очистки не передаются модели. Если тесты проходят,
но модель не убрала лишние файлы, это не полный успех демо.

## Автономная проверка конфликта

Без модели, ключа или сети доступен маленький сценарий восстановления:

```bash
hw-ai-agent workflow-demo --offline --mode safe
hw-ai-agent workflow-demo --offline --mode auto --crash-after-write
hw-ai-agent sessions
hw-ai-agent resume SESSION_ID
hw-ai-agent session SESSION_ID
```

`safe` в маленьком сценарии запрашивает четыре подтверждения: две записи и
два Bash. Аварийное демо выходит с кодом 86 после записи, но до сохранения
результата. `resume` ничего не повторяет, возвращает ошибку и состояние `uncertain`.
Скопируйте свой ID и ключ вызова (в маленьком демо `1:0`) и выберите одну ветку:

```bash
hw-ai-agent resolve SESSION_ID --call 1:0 --resolution retry
hw-ai-agent resume SESSION_ID

# Или: сохранить ошибку вызова и продолжить без повтора.
hw-ai-agent resolve SESSION_ID --call 1:0 --resolution skip
hw-ai-agent resume SESSION_ID

# Или: окончательно завершить с ошибкой.
hw-ai-agent resolve SESSION_ID --call 1:0 --resolution abort
```

Каждую ветку проверяйте на новой аварийной сессии. `skip` не делает откат;
в этом сценарии файл уже исправлен, поэтому тесты могут пройти и после `skip`.
После `abort` любые продолжения запрещены. `--stop-after-tools` демонстрирует
нормальную паузу после контрольной точки, а не такой конфликт.

Папки `workspace/workflow-*` исключены из Git. Отчёты очищаются от персональных
путей. Полная инструкция и сравнение вариантов восстановления:
[WORKFLOW_GUIDE.md](docs/WORKFLOW_GUIDE.md).

Одну сессию нельзя продолжать одновременно двумя процессами. Произвольный
инструмент и SQLite не образуют одну транзакцию: неопределённость между ними
требует проверки человеком. Сетевой запрос без сохранённого ответа может быть
повторён и повторно тарифицирован. Подробнее: [SESSION_RESULTS.md](docs/SESSION_RESULTS.md).

## Четвёртый блок: Plan Mode

Планирование — отдельная фаза той же сессии. До явного утверждения runtime
разрешает только `list_files` и `read_file`: запись, удаление и любой Bash
заблокированы в обоих режимах. Модель подаёт план через `submit_plan`.
План хранится как JSON: цель, упорядоченные шаги, инструменты каждого шага,
риски, допущения и проверяемые критерии готовности. Формат проверяет runtime.

```bash
# Настоящая модель из настроек:
hw-ai-agent plan --workspace ./workspace --mode safe "Исправь расчёт заказа; тесты не меняй"

# То же через обычный run:
hw-ai-agent run --plan --workspace ./workspace --mode auto "Исправь расчёт заказа"

# Контрольное демо с настоящей моделью:
hw-ai-agent demo --plan --provider ollama --model qwen3:4b-instruct --mode auto

# Plan demo с настоящей моделью из .env:
hw-ai-agent plan-demo --mode safe
hw-ai-agent plan-demo --mode auto

# Детерминированная проверка без модели и API:
hw-ai-agent plan-demo --offline --mode safe
hw-ai-agent plan-demo --offline --mode auto
```

Терминал показывает план и спрашивает: `y` — утвердить и сразу продолжить,
`n` — отклонить и завершить сессию без исполнения плана, Enter — сохранить
план на паузе. Ctrl+C или конец ввода также сохраняют ожидание решения.
Без интерактивного терминала автоматического утверждения нет; код 130.
После утверждения Safe по-прежнему подтверждает каждую запись и Bash,
Auto выполняет их сразу после проверок; удаления подтверждаются в обоих режимах.

Для продолжения достаточно команды без ID:

```bash
hw-ai-agent resume
```

Если есть одна незавершённая сессия, используется она; если несколько,
терминал предлагает выбрать номер из списка. План и решение сохраняются
в SQLite. Счётчик запросов к модели не сбрасывается при утверждении или resume.
В Plan Mode проверка тестов до утверждения не запускается даже при подготовке
демо; после исполнения проводится независимая проверка результата.

Для автоматизации сохранены явные команды:

```bash
hw-ai-agent session SESSION_ID
hw-ai-agent approve-plan SESSION_ID
hw-ai-agent reject-plan SESSION_ID
hw-ai-agent resume SESSION_ID
```

`approve-plan` сохраняет решение; отдельный `resume` начинает исполнение.
В `session` видны план и его состояние. Без терминала `resume` требует явный ID.
Файлы `workspace/plan-demo-*` исключены из Git. `plan-demo` по умолчанию
вызывает настоящую модель из `.env`, как `demo` и `workflow-demo`. Провайдер,
модель и файл настроек можно задать через `--provider`, `--model` и `--env-file`.
Модель сама изучает файлы, составляет план, а после утверждения исправляет код.
Фиксированный план и исправление используются только при `--offline`.
Примеры запуска с разными провайдерами:

```bash
hw-ai-agent plan-demo --provider openrouter --mode auto
hw-ai-agent plan-demo --provider ollama --model qwen3:4b-instruct --mode auto
hw-ai-agent plan-demo --provider openai --model gpt-4.1-mini --env-file .env.openai --mode auto
```

`--max-rounds` (20 без AGENT_MAX_ROUNDS) действует на всю сессию, `--max-tokens`
ограничивает ответ модели. Доступны `--policy`, `--approvals ask|deny` и
`--stop-after-tools`. При `resume` сохраняются исходная модель, лимиты и policy.
OpenRouter и OpenAI обращаются к API; `--offline` не требует ключа или сервера.

## Разрешение неопределённого вызова в терминале

При `resume` в интерактивном терминале runtime показывает неизвестный вызов,
его аргументы, текущее содержимое файла и сравнение с предложенной записью.
Доступны решения: повторить, считать вызов неуспешным и продолжить, завершить
с ошибкой или оставить сессию заблокированной. Для записи также доступно
подтверждение выполнения при точном совпадении байтов. Решение сохраняется;
после retry/skip/applied та же команда resume продолжает работу автоматически.
В Auto меню конфликтов также обязательно: неизвестный эффект не повторяется
без решения пользователя. `skip` и `abort` не откатывают уже сделанные изменения.

```bash
hw-ai-agent plan-demo --offline --mode auto --crash-after-write
hw-ai-agent resume
```

Первый запуск запросит утверждение плана, затем намеренно завершится кодом 86
после записи, до сохранения результата. Второй предложит решение прямо в терминале.
Без интерактивного stdin продолжение остаётся заблокированным: используйте
явный `resolve SESSION_ID --call KEY --resolution retry|skip|abort|applied`.
Команды с ID и пользовательским `--state-db` сохраняются для автоматизации.

## Уровень на 8 баллов: единый бюджет запуска

Лимиты задаются при старте `run`, `plan`, `demo`, `plan-demo` и `workflow-demo`.
Они относятся ко всему `run_id` (в CLI он называется ID сессии): планированию,
исполнению и восстановлению. При `resume`, утверждении плана и решении конфликта
счётчики не сбрасываются. Изменить модель или лимиты существующей сессии через
`resume` нельзя.

| Параметр | Что ограничивает | Без настройки в .env |
| --- | --- | --- |
| `--max-rounds` | Попытки обращения к модели, включая неуспешные | 12; у plan-demo/workflow-demo/rollback-demo — 20, tasks-demo — 30 |
| `--max-tool-calls` | Вызовы инструментов, включая ошибки, `submit_plan` и выдачу сохранённого результата | 128 |
| `--max-side-effects` | Потенциальные попытки записи, удаления и любого Bash | 32 |
| `--max-result-bytes` | Суммарные UTF-8 байты `content` результатов инструментов | 1 000 000 |

Для последних трёх лимитов разрешён ноль. Например, `--max-side-effects 0`
разрешает только изучать проект. `--max-tokens` по-прежнему ограничивает один
ответ модели; он не является общим бюджетом токенов или денег.

```bash
# Настоящая модель из .env; сначала план и его подтверждение:
hw-ai-agent plan --workspace ./workspace --mode safe \
  --max-rounds 20 --max-tool-calls 80 --max-side-effects 15 \
  --max-result-bytes 250000 "Исправь расчёт стоимости заказа. Тесты не меняй."

# Настоящая модель в демонстрационном проекте:
hw-ai-agent plan-demo --mode auto --max-tool-calls 80 \
  --max-side-effects 15 --max-result-bytes 250000

# Детерминированная проверка всех четырёх бюджетов без API и подтверждений:
hw-ai-agent budget-demo

# Продолжение со всеми сохранёнными лимитами и расходами:
hw-ai-agent resume
```

Терминал показывает расход и лимит каждого бюджета. `hw-ai-agent session SESSION_ID`
выводит сохранённые `limits`, `spent` и `remaining`. При нехватке ресурса запуск
останавливается со статусом `budget_exhausted` и причиной `BUDGET_EXHAUSTED`.
Изменения, сделанные до остановки, сохраняются; автоматического отката нет.
Для новой работы с другими лимитами создайте новый запуск.

Вся пачка проверяется до первого исполнения. Число вызовов и потенциальных
опасных действий списывается атомарно с сохранением предложенных вызовов в
состоянии `pending`. Если лимита не хватает хотя бы по одному измерению, ни
один вызов не начинается; отклонённая пачка сохраняется в событиях. Резерв
сохраняется и для ещё не исполненных вызовов. Отказ policy или оператора не
возвращает резерв вызова и потенциального опасного действия. Получение
сохранённого результата старого `tool_call_id` расходует вызов и байты, но
не списывает второе опасное действие и не повторяет изменение файла.
Явный `retry` после сбоя требует нового резерва вызова и опасного действия.

Перед стартом инструмента доступные байты резервируются атомарно со статусом
`running`; ограничение передаётся инструменту. Квота учитывает общий остаток,
предел результата конкретного инструмента и оставляет минимум один байт для
каждого следующего результата пачки. Runtime обрезает весь результат, включая
заголовки stdout/stderr и сообщения об ошибках. Неполный вывод помечается
`[TRUNCATED: result budget]`; при квоте меньше размера метки используется `~`.
Метка тоже входит в бюджет, а UTF-8 символы не разрываются.

При обычном завершении атомарно сохраняются результат и его фактический размер;
неиспользованная часть резерва освобождается. При прерывании до этого сохранения
весь зарезервированный объём остаётся потраченным: `resume`, `skip`, `applied`
и повтор не возвращают его. Поэтому после сбоя расход может быть больше суммы
доступных результатов. История списаний и расчётов хранится вместе с сессией.

SQLite-схема версии 5 мигрирует старые сессии версий 1/2/3 без удаления истории
и планов. Уже известный расход восстанавливается по сохранённым попыткам и
результатам; для ещё не начавшейся пачки резерв проверяется перед продолжением.
Отсутствующий или повреждённый бюджет новой сессии блокирует продолжение.

Демо создаёт временные учебные папки и заканчивается `BUDGET DEMO PASS`.
Оно проверяет четыре остановки, отказ исполнить первую операцию слишком большой
пачки, сохранение счётчиков при resume, обрезание вывода и отсутствие возврата
бюджета после сбоя. Настоящий аварийный выход также проверяется в тестах:
процесс завершается между списанием/действием и сохранением результата.

```bash
python -m unittest discover -s tests -p test_budget.py -v
```

У контрольных демо подготовка файлов, исходный запуск тестов и независимая
проверка результата относятся к проверочной обвязке вне агентского запуска.
Бюджет охватывает все вызовы агента; проверочная обвязка не выдаётся за его действия.
Обычный `run` больше не запускает предварительный Bash вне бюджета. Для отдельной
диагностики окружения используйте `hw-ai-agent doctor`.

## Уровень на 9 баллов: задачи с зависимостями

`plan --tasks`, `run --tasks` и `demo --tasks` включают планирование с управляемыми
задачами. `--tasks` автоматически включает Plan Mode. Обычный Plan Mode и старые
сессии сохраняют прежний формат; задачи старых планов не создаются задним числом.

Каждый шаг нового плана содержит `id`, `description`, `tools`, `depends_on`
и `verification`. Runtime проверяет уникальность ID, ссылки на зависимости,
отсутствие циклов и доступность инструмента проверки. Пользователь видит
зависимости и критерии результата при утверждении плана. До утверждения все
задачи находятся в состоянии `pending`, разрешено только чтение.

Runtime последовательно выбирает первую доступную задачу, чьи зависимости
успешно завершены, и сохраняет её состояние `running`. Каждая операция исполнения,
включая `complete_task` и `fail_task`, связана с выбранным `task_id` в хранилище.
Вызовы при планировании записываются отдельно с фазой `planning` и без `task_id`.
Модель получает разрешённые для текущей задачи инструменты и не может выбрать
другую задачу или перенести старый `tool_call_id` между задачами.

`complete_task(task_id)` должен быть последним вызовом в пачке. Runtime проверяет
успешный результат обычного инструмента именно этой задачи и сохраняет
подтверждение вместе с завершением задачи и результатом `complete_task` одной
транзакцией. Текст модели «готово» или предложенное ею доказательство задачу не
закрывают. Поддерживаются следующие критерии:

| `verification.kind` | Что проверяется |
| --- | --- |
| `file_written` | Был успешный `write_file` для указанного пути; фактические байты файла совпадают с предложенной записью |
| `file_read` | Был успешный `read_file`; текущее содержимое совпадает с сохранённым результатом чтения |
| `file_absent` | Был успешный `delete_file`; файл действительно отсутствует |
| `tests_passed` | Указанный unittest запущен через Bash в заданном cwd; код 0, ненулевое число тестов и полный результат `OK` |

Подтверждение содержит тип критерия, ключ фактического вызова и SHA-256 его
результата. При resume связь подтверждения с сохранённым результатом проверяется.
Проверка файла описывает выполненную операцию; правильность поведения кода
подтверждается отдельной задачей с тестами. Проверки файлов соблюдают границы
workspace и policy; они не обходят явный запрет чтения. Верификатор не запускает
скрытый Bash: тестовый запуск — обычный вызов с бюджетом и подтверждением Safe.

Неудачная проверка возвращает ошибку модели и оставляет задачу активной:
можно исправить код или выполнить нужную проверку. `fail_task(task_id, reason)`
фиксирует невозможность выполнить задачу; её зависимые задачи блокируются.
Независимые задачи могут продолжаться. Наличие неуспешных/заблокированных задач
не позволяет завершить сессию успешно.

Задачи выводятся в stdout как чеклист: `[ ]` — ожидание, `[>]` — исполнение,
`[x]` — проверенное завершение, `[!]` — ошибка, `[-]` — блокировка зависимостью.
Их состояния и подтверждения сохраняются вместе с run_id. После resume
завершённые задачи не запускаются снова. Бюджет четырёх ресурсов остаётся общим
для всей сессии, включая управление задачами, восстановление и явные повторы.
Схема SQLite версии 5 добавляет таблицы задач и связей вызовов без удаления
старых планов, истории или потраченного бюджета.

```bash
# Свой проект, настоящая модель из .env:
hw-ai-agent plan --tasks --workspace ./workspace --mode safe --max-rounds 30 \
  "Исправь расчёт заказа, проверь результат тестами. Тесты не меняй."

# Новое демо с настоящей моделью по умолчанию:
hw-ai-agent tasks-demo --mode auto
hw-ai-agent tasks-demo --provider ollama --model qwen3:4b-instruct --mode auto

# Воспроизводимое демо без API:
hw-ai-agent tasks-demo --offline --mode auto

# Пауза после первой проверенной задачи, затем продолжение без ввода ID:
hw-ai-agent tasks-demo --offline --mode auto --stop-after-tasks 1
hw-ai-agent resume

# Настоящий аварийный выход после записи до сохранения её результата:
hw-ai-agent tasks-demo --offline --mode auto --crash-after-write
hw-ai-agent resume
```

Демо создаёт ошибочные `tax.py`, `receipt.py` и неизменяемый `test_checkout.py`.
В offline-варианте три задачи: исправить налог 20%, исправить сумму чека после
первой задачи, проверить оба исправления четырьмя тестами. Настоящая модель сама
читает проект, составляет план минимум из трёх задач и выбирает исправления.
Без явного `--offline` подставной клиент не используется. Настройки провайдера,
модели и лимитов сохраняются для resume. Без AGENT_MAX_ROUNDS/AGENT_MAX_TOKENS
у нового демо 30 запросов и 3072 токена на ответ; остальные бюджеты имеют обычные значения.

Утверждение плана и разрешение неопределённого вызова происходят в терминале.
Safe подтверждает каждую запись/Bash и удаление; Auto подтверждает каждое удаление.
`--stop-after-tasks N` также доступен у run/plan/demo и resume; он не меняет лимиты.
Успешное демо заканчивается `TASKS DEMO PASS` и сохраняет `tasks-report.json`:
чеклист, подтверждения результатов, общий бюджет и независимую проверку тестов.
Подготовка файлов и независимая проверка относятся к обвязке вне бюджета агента.

```bash
python -m unittest discover -s tests -p test_tasks.py -v
REQUIRE_SANDBOX_TESTS=1 python -m unittest discover -s tests -p test_tasks.py -v
```

Тесты проверяют минимум три задачи, зависимости, запрет текстового завершения,
фактические результаты, resume без повторения завершённой задачи, общий бюджет,
сохранение Safe/Auto, повреждённые подтверждения и атомарность фиксации результата.
Проверяется настоящий аварийный выход между записью файла и checkpoint, после
которого runtime блокирует молчаливый повтор и предлагает обычное разрешение конфликта.

## Уровень на 10 баллов: журнал и безопасный откат

`--journal` включает журнал при старте run/plan/demo/plan-demo/workflow-demo/tasks-demo.
Он сохраняется по run_id в той же приватной SQLite-базе вне workspace и работает
после перезапуска. Для старой сессии без журнала исходное содержимое нельзя
восстановить задним числом: команда отката такую сессию отклоняет.

```bash
# Все возможности: план, задачи, общий бюджет, журнал изменений:
hw-ai-agent plan --tasks --journal --workspace ./workspace --mode safe --max-rounds 30 \
  "Исправь расчёт заказа и проверь его тестами. Тесты не меняй."

# Новое демо с настоящей моделью из .env; журнал включён автоматически:
hw-ai-agent rollback-demo --mode auto

# То же воспроизводимо без API:
hw-ai-agent rollback-demo --offline --mode auto

# Просмотр и откат: терминал предложит выбор сессии без поиска ID:
hw-ai-agent changes
hw-ai-agent rollback

# Для автоматизации доступны явный ID и путь базы:
hw-ai-agent changes SESSION_ID --state-db .agent/sessions.sqlite3
hw-ai-agent rollback SESSION_ID --state-db .agent/sessions.sqlite3
```

`rollback-demo` использует контрольный проект order.py/test_order.py: агент
читает файлы, предлагает план, после подтверждения исправляет формулу и запускает
тесты через Bash. Демо заканчивается `DEMO PASS`; затем changes показывает diff,
а отдельная явная команда rollback возвращает исходную ошибочную формулу.
Модель, провайдер, лимиты, Safe/Auto и resume работают как у plan-demo.
`tasks-demo --journal` показывает журнал вместе с задачами уровня 9.

Перед первой операцией создаётся исходный снимок разрешённого дерева workspace.
Перед каждой записью/удалением/Bash runtime снова снимает дерево, сравнивает его
с последним checkpoint и сохраняет снимок до действия. Если список путей,
содержимое, режим файла или идентичность корня отличаются, операция останавливается
до изменения файлов. После действия сохраняются фактические изменения,
снимок, SHA-256 и состояние операции. Непредвиденные изменения требуют явного
разрешения неопределённого вызова.

Для каждого затронутого пути журнал хранит состояние до первой правки и после
последней. Содержимое сохраняется как байты, поэтому CRLF, бинарные файлы и пустые
файлы восстанавливаются точно. Повторные записи не заменяют первоначальную копию.
Общий diff и хеши доступны даже после завершённого отката. Данные исходных файлов
хранятся в базе с правами 0600 и не публикуются в Git; одинаковое содержимое
сохраняется один раз по SHA-256.

Снимок охватывает исходники и тесты в разрешённых policy директориях. Симлинки
учитываются как записи без чтения их целей и не обходятся при откате.
Hard links и неподдерживаемые специальные файлы отклоняются. Для полного снимка
нужны разрешённые чтения; явный deny/ask не обходится. Пределы снимка: 2000 путей,
10 MiB на файл и 20 MiB содержимого дерева. Эти пределы не являются бюджетом модели.

Из снимков исключены защищённые .git/.venv/.idea/.agent, секретные .env* и
генерируемый __pycache__. Только у соответствующих демо исключены их корневые
JSON-отчёты: demo-report.json, workflow-report.json или tasks-report.json.
Модель не может менять исключённый файл отчёта при включённом журнале. Эти
исключения не скрывают order.py/test_order.py или другие разрешённые исходники
и тесты. Обычные JSON-файлы проекта учитываются.

Bash остаётся изолированным процессом с запретом записи всего workspace и сети.
Журнал проверяет дерево и вокруг Bash; команда не может скрыто изменить
исходники. Новые файлы, появившиеся вне разрешённой файловой операции, не
приписываются агенту автоматически.

Откат сначала проверяет весь набор затронутых файлов: текущие хеши, содержимое
сохранённых копий, канонические пути, отсутствие симлинков/hard links,
защиту тестов и актуальный policy. При чужой правке хотя бы одного из них
не начинается ни одно восстановление. Остальные файлы, включая новые внешние
файлы, не откатываются. Перед первой записью проверки повторяются после получения
всех подтверждений. Safe подтверждает каждое восстановление записи; удаление
созданного агентом файла подтверждается и в Safe, и в Auto.

Неиспользованные пустые каталоги могут оставаться: откат управляет файлами и
не удаляет каталоги с чужими данными. Права обычного файла восстанавливаются;
владельцы, ACL и расширенные атрибуты не изменяются.

Откат — административная операция по явной команде человека, доступная даже
после исчерпания бюджета агента. Он не возвращает и не сбрасывает потраченный
бюджет. После успешного отката сессия становится rolled_back; продолжить её
исполнение нельзя. Для новой задачи создайте новый запуск.

Если процесс прервался во время отката, журнал остаётся rollback_pending.
Повторная явная команда rollback проверяет хеши и продолжает только оставшиеся
операции. Неожиданное состояние файла вызывает конфликт; принудительного
перезаписывания нет. Файловые операции используют проверенные дескрипторы
и повторную проверку целей. Несколько файлов не являются одной атомарной
транзакцией файловой системы; ход отката сохраняется для восстановления после сбоя.

### Неопределённый вызов после сбоя

До отката требуется разрешить неопределённый tool call. Терминальный resume
показывает предложенный вызов и сравнение файлов. После выбора retry/skip/applied/abort
показываются все изменения относительно снимка до вызова и запрашивается их
принадлежность: own — отнести к сессии, external — считать внешними. При отсутствии
явного ответа вызов остаётся заблокированным. Изменения, появившиеся после
просмотра, нельзя приписать без нового просмотра и подтверждения.

```bash
hw-ai-agent rollback-demo --offline --mode auto --crash-after-write
hw-ai-agent resume

# Неинтерактивное явное решение:
hw-ai-agent resolve SESSION_ID --call 3:0 --resolution applied --changes own
hw-ai-agent rollback SESSION_ID
```

Ключ вызова берите из `session SESSION_ID`; в разных сценариях он отличается.
`applied` по-прежнему требует точного совпадения байтов записи. own включает
показанные фактические изменения в журнал; external исключает их из отката
этого вызова и не разрешает молча менять новую внешнюю версию. Если внешняя правка
затронула более ранний собственный результат, его откат тоже будет заблокирован.
Отклонение повтора или завершение с ошибкой не выполняют автоматический откат.

```bash
python -m unittest discover -s tests -p test_journal.py -v
REQUIRE_SANDBOX_TESTS=1 python -m unittest discover -s tests -p test_journal.py -v
```

Детерминированные проверки показывают изменение order.py, diff и восстановление
исходных байтов после перезапуска; создание/удаление, бинарные файлы, отсутствие
частичного отката при конфликте или отказе подтверждения, повторную проверку
policy, аварийный выход, явную принадлежность изменений и прерванный откат.
Новая схема SQLite версии 5 добавляет журнал без удаления старой истории,
планов, задач или бюджета. Старая сессия сохраняет прежний режим.

В этой версии реализованы цикл агента, инструменты, policy, режимы Safe/Auto,

и подтверждением результатов (9 баллов), журнал изменений и безопасный откат
по явной команде пользователя (10 баллов).
