# Второй блок: контроль разрешений

В доступном чате после первого блока указан `policy`; полного официального
условия второго блока нет. Реализованы разрешение, подтверждение и запрет
действий модели. Точное соответствие критериям баллов требует их полного текста.

## Реализация

- `src/hw_ai_agent/policy.py`: неизменяемые правила, `allow / ask / deny`,
  проверка JSON и приоритет явного запрета.
- `ToolRuntime.execute()`: проверяет обязательные ограничения, затем policy,
  запрашивает подтверждение для `ask` и только после разрешения вызывает инструмент.
- `cli.py`: показывает diff перед записью, принимает подтверждение одного
  вызова, поддерживает `--policy` и `--approvals ask|deny`.
- `policies/`: готовые профили `readonly`, `review`, `demo`.
- `policy_demo.py`: проверка разрешений без API и настоящей модели.
- `demo.py`: сохраняет `policy_events` рядом с результатами модели.
- `filesystem.py`: фиксирует цель записи и проверяет открытый файл до изменения.

Все вызовы инструментов от модели проходят через `execute()`. Инициализация
workspace и независимая проверка тестов остаются доверенными действиями приложения.
Ни правила, ни подтверждение не отменяют защиту контрольных тестов и секретов
или системную песочницу.

## Проверено

Полный локальный прогон после исправлений: **66 тестов, без ошибок и пропусков**:

```bash
REQUIRE_SANDBOX_TESTS=1 python -m unittest discover -s tests -v
```

Первоначальные 21 проверки policy подтверждают приоритет `deny`, проверку конфигураций,
подтверждение и отказ, неизменность файла при отказе, отсутствие повторного
использования разрешения, нормализацию путей и невозможность обойти запреты
runtime через `allow`. Повторно прошли 27 проверок первого блока, включая
реальные проверки системной песочницы.

Автономная демонстрация:

```bash
hw-ai-agent policy-demo
```

Результат: **POLICY DEMO PASS**, все девять сценариев успешны. Это проверка
runtime с подставными подтверждениями, а не самостоятельное решение модели.

## Проверка с моделью

Реальная демонстрация с `deepseek/deepseek-v3.2`
через OpenRouter и профилем `policies/demo.json` завершилась **DEMO PASS**.
Модель исправила `order.py`, сама запустила 6 контрольных тестов, независимая
проверка также прошла. SHA-256 `test_order.py` до и после совпал.
Разрешения всех запросов модели проверены runtime и сохранены в `policy_events`.
Полный отчёт для репозитория: [policy-deepseek-demo-report.json](policy-deepseek-demo-report.json).
Этот запуск подтверждает работу заранее заданных правил с настоящей моделью;
ручные отказы и подтверждения проверены отдельно автономными тестами.
Сохранённый отчёт относится к версии до последующего усиления файловых прав.
После исправлений исходный сценарий демо повторно проверен с подставной моделью
и настоящими инструментами; повторный платный API-запрос не выполнялся.

После установки и настройки ключа из [README](../README.md) можно выполнить:

```bash
hw-ai-agent demo --provider openrouter --model deepseek/deepseek-v3.2 --policy policies/demo.json --approvals deny
```

Профиль разрешает модели менять только `order.py` и запускать одну конкретную
команду тестов. Успех подтверждают `DEMO PASS`, неизменность тестов и журнал
`policy_events` в отчёте нового запуска.

Для проверки ручного подтверждения запустите `demo` без `--policy`: перед
записью появятся diff и вопрос `[y/N]`. Ответ `n` должен сохранить исходный
файл. Отказ от необходимого исправления приводит к `DEMO FAIL` — это ожидаемо,
так как задача не выполнена, хотя проверка разрешения отработала корректно.

## Исправления найденных обходов

Добавлены 18 проверок в `tests/test_policy_security.py`.
Два ключевых теста сначала запускались на старом коде: оба упали, обнаружив
обход через Bash и перенаправление записи после подтверждения. На исправленной
версии они проходят вместе со всем набором.

1. **Побочные эффекты Bash:** дочерние процессы не имеют права записи файлов
   workspace. Проверено, что импорт разрешённого `order.py` не может создать
   другой файл, а запись не может затронуть даже файл с правилом `write_file: allow`.
   Ограничения чтения policy применяются и внутри процесса: запрещённые файлы
   недоступны через прямой путь, симлинк или имя с переносом строки.
   Файлы с решением `ask` не становятся доступны из-за подтверждения команды.
2. **Смена цели после подтверждения:** фиксируются канонический путь, идентичность
   и состояние файла, идентичность существующих родительских каталогов.
   Замены и ручные правки во время ожидания блокируются с `TARGET_CHANGED`.
   Открытие через дескрипторы каталогов с `O_NOFOLLOW` не позволяет перенаправить
   запись симлинком непосредственно перед открытием. Содержимое изменяется
   только после проверки открытого файла; неожиданно появившийся файл
   не перезаписывается.

Строгий Bash не поддерживает тесты с записью файлов или созданием временных
файлов. Шаблоны чтения с `[]`, которые невозможно перенести в этот профиль,
приводят к отказу запуска, а не к ослаблению защиты. Это ограничения текущей версии.

Функциональная проверка с подставной моделью подтвердила, что законное исправление
`order.py` через `write_file`, все шесть контрольных тестов и независимая
повторная проверка по-прежнему дают `DEMO PASS`.
