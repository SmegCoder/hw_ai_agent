# Третий блок: сохранение и продолжение работы

В доступном плане третий блок обозначен как восстановление. Полного официального
условия нет. Реализованы журнал сессии, продолжение после остановки и безопасная
обработка инструментов с неизвестным результатом.

## Файлы и механизм

- `session.py`: SQLite, атомарные записи истории и результатов, состояния
  вызовов, блокировка параллельного продолжения и решения неопределённых действий.
- `agent.py`: сохраняет ответ модели и список вызовов до исполнения; отмечает
  вызов как начатый до возможных эффектов; сохраняет результат и событие одной
  транзакцией. При продолжении загружает историю и исполняет только оставшиеся шаги.
- `session_demo.py`: остановка после сохранённой записи, новое подключение
  к базе и продолжение без повторного изменения файла.
- `cli.py`: `sessions`, `session`, `resume`, `resolve`, `session-demo`,
  `--state-db`, `--stop-after-tools`.
- `tests/test_session.py`: 25 новых проверок восстановления и CLI.

Состояния вызова: `pending` → `running` → `completed`/`failed`.
Оставшийся после сбоя `running` у записи становится `uncertain`.
Завершённые шаги пропускаются; незавершённые действия только для чтения
можно повторить, а неопределённые записи автоматически не повторяются.

История содержит исходные `tool_call_id` и аргументы; несколько вызовов одного
ответа продолжаются в исходном порядке. Счётчик модельных запросов и лимиты
сохраняются. Смена workspace, policy, модели, адреса сервера или ограничений
runtime приводит к отказу продолжения. Старые подтверждения не переиспользуются.

База `.agent/sessions.sqlite3` находится вне workspace, исключена из Git
и недоступна файловым инструментам модели. Настройки сохраняются по явному
списку полей без API-ключа. База не зашифрована и содержит рабочую историю.

## Проверки

Полный набор: **91 тест прошёл без ошибок и пропусков**:

```bash
REQUIRE_SANDBOX_TESTS=1 python -m unittest discover -s tests -v
```

Проверены: новое подключение к базе после остановки, порядок оставшихся вызовов,
отсутствие повтора завершённой записи, свежие подтверждения при явном retry,
блокировка неопределённого действия, проверка applied, сохранение счётчика,
смена конфигурации, параллельное продолжение, приватные права базы и отсутствие
ключа из настроек в сохранённых данных. Дочерний процесс завершался через
`os._exit()` после файлового эффекта: восстановление заблокировало повтор.
Проверен также отказ сохранения результата после эффекта.

Автономная демонстрация дала **SESSION DEMO PASS**: запись выполнена один раз,
после открытия новой базы выполнены ожидающие тесты, все шесть контрольных
тестов прошли, контрольный файл не изменён. Это подставная модель с настоящими
инструментами, не платный API-запрос.

## Ручная проверка

Проверено продолжение с настоящей локальной
`qwen3:4b-instruct`. Сессия `04fbc928c85e47bc98272fa07945377e` остановилась
после первого сохранённого результата `list_files` с кодом 130. Новый процесс
`resume` продолжил счётчик с обращения 2, прочитал файлы, выполнил одну запись
`order.py`, запустил тесты и завершил ту же сессию. Все шесть тестов и независимая
проверка прошли, контрольный файл остался неизменным: **DEMO PASS**.
В журнале только один `list_files`: сохранённый шаг не повторился.
Полный отчёт: [session-ollama-demo-report.json](session-ollama-demo-report.json).
Платный API не использовался. В отдельной автономной демонстрации и тестах
проверена также остановка именно после записи без её повторного исполнения.

Установка описана в [README](../README.md). Для проверки на Ollama:

```bash
hw-ai-agent demo --provider ollama --model qwen3:4b-instruct --policy policies/demo.json --approvals deny --stop-after-tools 1
hw-ai-agent sessions
hw-ai-agent resume SESSION_ID
```

Замените `SESSION_ID` на ID из вывода. Первая команда намеренно завершается
кодом 130 после контрольной точки. `resume` продолжает эту же сессию и повторно
проверяет результат демо; при успехе выводит `DEMO PASS`.

Если запись имеет неизвестный результат, используйте `session` для просмотра,
проверьте файлы и затем `resolve --call KEY --resolution applied|retry|skip`.
`applied` требует совпадения текущих байтов файла с предложенным содержимым.
`retry` — явное решение оператора повторить вызов, а не автоматический повтор.

Произвольные файловые эффекты и запись в SQLite не образуют одну транзакцию;
неопределённость между ними не скрывается. Сетевой запрос без сохранённого ответа
может повториться. Rollback, Plan Mode и полноценный денежный бюджет — следующие блоки.
