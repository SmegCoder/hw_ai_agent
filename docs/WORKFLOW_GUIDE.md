# Многофайловое демо: режимы, удаление, восстановление

## Текущие режимы

| Действие | safe | auto |
|---|---|---|
| Чтение и список файлов | Сразу, если policy разрешает | Сразу, если policy разрешает |
| Запись | Подтверждение каждого вызова | Сразу после проверок |
| Bash | Подтверждение каждого вызова | Сразу после проверок |
| Удаление | Подтверждение каждого вызова | Подтверждение каждого вызова |

Явные запреты policy, ограничения путей и команд, защита тестов и секретов
остаются обязательными. В Safe policy-`allow` не отменяет подтверждения.
В Auto запись и Bash выполняются сразу после проверок, без разрешений на
сессию. Удаление подтверждается каждый раз в обоих режимах, включая `resume`.
Это правила PDF; старые разрешения на сессию не используются.

## Сценарий с настоящей моделью

```bash
source .venv/bin/activate
hw-ai-agent workflow-demo --provider openrouter --mode safe
hw-ai-agent workflow-demo --provider openrouter --mode auto
```

Каждая команда создаёт отдельную папку и сессию. Ключ и модель OpenRouter
берутся из существующего `.env`. Эти запуски обращаются к платному API.
Если хотите другую модель, добавьте `--model` с её точным ID.
Локальный вариант без платы за API:

```bash
hw-ai-agent workflow-demo --provider ollama --model qwen3:4b-instruct --mode auto
```

Восемь исходных файлов: два модуля с ошибками, два нужных модуля зависимостей,
защищённый файл из четырёх тестов и три лишних модуля. В промпте нет перечня
лишних файлов и требования удалить именно их. Он просит разобраться в проекте,
исправить ошибки и оптимизировать код, сообщает о возможности чтения, создания,
изменения, удаления и запуска тестов. Модель сама выбирает действия.

В `safe` на каждый изменяющий вызов и Bash появится вопрос `[y/N]`; перед записью
показывается diff, перед удалением — файл и размер. В `auto` вопросы появляются
только при каждом удалении. Если отказать, действие не выполняется.
`--approvals deny` подходит для отказа в новых подтверждениях,
а не для автоматического согласия. Без интерактивного stdin новый запрос
сохраняется в `awaiting_approval`, запуск останавливается с кодом 130.
`resume` в терминале позволяет подтвердить или отклонить действие.

Отчёт `workflow-report.json` показывает:

- `functional_success`: четыре теста прошли, контрольный файл не изменён;
- `cleanup_complete`: убраны минимум два из трёх неиспользуемых модулей;
- `removed_optional_files`: что именно убрано;
- `permission_requests`: число запросов разрешений;
- `events`, `usage`, модель и ID сессии.

`WORKFLOW DEMO PASS` требует корректности и очистки одновременно. Модель может
исправить ошибки, но не решить удалить лишние модули: это будет функциональный
успех, но не полный успех сценария. Заранее гарантировать её решение нельзя.
Критерий очистки находится только в независимом проверяющем коде и не передаётся
модели. Предел — 20 обращений по умолчанию; лимит можно задать через `--max-rounds`.

## Восстановимое удаление

`delete_file` работает только с обычными файлами внутри workspace. Нельзя удалить
тесты, секреты, каталоги, симлинки и файлы с жёсткими ссылками. Перед действием
проверяются ограничения и состояние цели; подмена во время подтверждения блокируется.
Файл перемещается в `.agent/trash/RECOVERY_ID/file`, `info.json` содержит исходный
путь. Эта папка вне workspace и недоступна модели. При своём `--state-db` папка
`trash` располагается рядом с базой. Данные не зашифрованы и не должны публиковаться.

Удалённый файл можно восстановить копированием сохранённого `file` на прежнее
место из `info.json`, предварительно проверив, что там нет нужной новой версии.
Автоматического отката нет. Перенос между разными файловыми системами отклоняется
без удаления исходного файла. При гонке непосредственно в момент переноса
перемещённый объект сохраняется в восстановимой папке, а выполнение сообщает ошибку.

## Воспроизводимый конфликт без модели

```bash
hw-ai-agent workflow-demo --offline --mode auto --crash-after-write
hw-ai-agent sessions
hw-ai-agent resume SESSION_ID
hw-ai-agent session SESSION_ID
```

`--offline` использует маленький детерминированный сценарий: три файла, две записи и два
Bash, подставная модель и настоящие инструменты. Для проверки вопросов запустите
его с `--mode safe`: будет четыре подтверждения. В Auto запись и Bash
выполняются без вопросов.
Он не проверяет способность настоящей модели обнаружить неиспользуемые файлы.

При `--crash-after-write` происходит настоящий `os._exit(86)` после изменения
первого файла, но до фиксации результата. Первая команда возвращает код 86.
`resume` переводит `running` в `uncertain`. В интерактивном терминале
он показывает действие, состояние файла и меню решений. Без терминала
возвращает код 1 и ничего не повторяет автоматически.
Для ручного `resolve` в `session` смотрите первый элемент `unfinished_calls`; в этом сценарии ключ `1:0`.

Обычный ручной сценарий: `hw-ai-agent resume` без ID, выбор сессии по номеру
и решения конфликта в терминале. Для автоматизации выберите один вариант с ID:

```bash
# Повторить инструмент и продолжить:
hw-ai-agent resolve SESSION_ID --call 1:0 --resolution retry
hw-ai-agent resume SESSION_ID

# Сохранить ошибку вызова и продолжить без повтора:
hw-ai-agent resolve SESSION_ID --call 1:0 --resolution skip
hw-ai-agent resume SESSION_ID

# Окончательно завершить с ошибкой:
hw-ai-agent resolve SESSION_ID --call 1:0 --resolution abort
```

Для каждой ветки нужна новая аварийная сессия. `skip` не откатывает уже сделанную
запись: поэтому в этом сценарии тесты после него проходят. `abort` возвращает
код 1 и запрещает дальнейшее продолжение. `retry` повторяет только инструменты
с поддержанным контрактом; удаление уже отсутствующего файла не делает новый
перенос. Повтор проходит все ограничения режима. Неизвестный инструмент повторять
нельзя. Дополнительное `applied` проверяет точное содержимое записанного файла.

## Проверки

Полный набор: 201 тест без ошибок и пропусков. При обычном запуске без
`REQUIRE_SANDBOX_TESTS=1` пропускается 24 системных теста.

```bash
REQUIRE_SANDBOX_TESTS=1 python -m unittest discover -s tests -v
```

Проверены режимы, запрет обхода подтверждений через `allow`, отказы, удаление
с восстановлением, защищённые цели, подмена файла перед переносом, неопределённое
удаление, отсутствие подтверждений записи и Bash в Auto, продолжение после
перезапуска и невозможность использовать старое разрешение на удаление.
Расширенный сценарий проверен подставными ответами модели с
настоящими инструментами в обоих режимах; отсутствие очистки не засчитывается
как полный успех. Отдельные процессы проверяют реальный сбой и все три решения.

Два реальных локальных прогона с `qwen3:4b-instruct` исправили ошибки и прошли
четыре теста, но модель не выбрала удаление неиспользуемых модулей. Итог —
функциональный успех, `cleanup_complete=false`, не полный `WORKFLOW DEMO PASS`.
Это результат выбора модели, а не подтверждение удаления. Сохранён
[очищенный отчёт последнего прогона](workflow-ollama-partial-report.json).
Платный API для этих проверок не вызывался. Сохранённый локальный отчёт
относится к предыдущим режимам; новая семантика подтверждений проверена
автоматическими тестами с настоящими инструментами и подставными ответами модели.
